## 1. 产品结论

### 1.1 一句话定位

Open Compute System 是面向 GPU 资源运营方的自托管 AI 推理商业化基础设施。平台连接客户自有 GPU 或固定合作方资源，统一完成资源纳管、模型部署、OpenAI 兼容 API 发布、API Key、Token 计量计费、GPU 实例交付和运营管理。

对外传播建议：

> 把自有 GPU，发布成可计费的模型 API。

### 1.2 产品品类

产品不是硬件一体机、公共 GPU 撮合市场，也不是 Kubernetes/GPU 底层调度器。它是一套部署在资源方环境中的平台软件，位于 GPU/现有调度系统与最终 API 用户之间：

    自有 GPU / 固定合作方 API / 现有调度系统
                         ↓ Resource Adapter
              Open Compute System 控制面
          资源池、模型部署、实例、订单、审计
                         ↓
        推理网关、API Key、限流、Token 计量计费
                         ↓
          资源方自有品牌的模型 API 与用户控制台

### 1.3 首要商业假设

目标客户已经拥有 GPU 或稳定上游，但缺少把硬件持续转化为模型 API 收入的平台软件。目前通常需要人工部署模型、暴露推理端口、分发共享密钥和手工统计用量，或者只能按小时出租 GPU，无法按 Token 运营自己的模型服务。

产品价值不是提供更便宜的 GPU，而是让资源方：

1. 用自有品牌发布 OpenAI 兼容模型 API；
2. 在 GPU 实例出租与模型 API 服务之间分配资源；
3. 自动管理 API Key、额度、限流、Token 用量和账单；
4. 保留自己的客户、价格、成本、模型和经营数据；
5. 在不替换底层资源系统的前提下建立可复制的推理服务。

### 1.4 当前阶段

当前是技术 MVP，不是可直接宣称生产可用的 AI 推理商业平台：

- 已完成：GPU SKU 与实例闭环、OpenAI-compatible 推理 Adapter、模型/副本运营、API Key、RPM/TPM、Token 用量与扣费、Docker vLLM 节点 Agent、部署状态和运营页面；
- 当前限制：本地种子资源和模型仍使用 Mock；节点 Agent 只通过模拟 Docker runner 验证，尚未在真实 NVIDIA GPU、Docker socket、vLLM 模型下载和 Redis 多进程环境中验收；
- 下一阶段主目标：在一个真实私有环境中，通过节点 Agent 启动 vLLM，把模型发布成可鉴权、可计量、可收费、可运营的 API，同时保留 GPU 实例出租能力。

### 1.5 已确认的首期部署决策

| 决策项 | 首期方案 | 后续方向 |
|---|---|---|
| 交付形态 | 完全私有部署，控制面、数据库、网关和 Agent 均在客户环境 | 不建设厂商托管多租户 SaaS |
| 推理运行时 | vLLM | 按客户需求增加 NVIDIA NIM 等 Adapter |
| GPU 节点执行层 | 单机 Docker 节点 Agent | Kubernetes/KServe/NIM Operator |
| 控制方式 | 控制面调用节点 Agent 的受控 API | 不通过任意 SSH 命令管理节点 |
| 模型来源 | 客户提供具备商业使用权的模型 ID、权重和访问凭据 | 增加内部模型模板与许可证记录 |

## 2. 用户与购买决策

### 2.1 主要客户：资源运营方

| 客户类型 | 当前问题 | 购买动机 | 首期适配度 |
|---|---|---|---|
| 中小 GPU 机房/运营商 | 有卡但缺少模型部署、API 网关和计费系统 | 快速推出自有品牌模型 API | 最高 |
| AI 解决方案公司 | 有固定资源和行业客户，推理交付依赖人工 | 统一模型服务、Key、用量与账单 | 高 |
| IDC/服务器渠道商 | 只能卖硬件或按时出租，缺少软件收入层 | 将 GPU 包装为持续收费的 API 服务 | 高 |
| 企业/高校内部平台团队 | GPU 与模型服务分散，缺少统一配额 | 内部 API、项目配额和成本追踪 | 中，需团队版能力 |
| 个人闲置 GPU 主机 | 资源少、网络和运维能力不稳定 | 出租闲置资源 | 暂不服务 |

### 2.2 系统使用者

| 角色 | 核心任务 |
|---|---|
| 资源方负责人 | 看 GPU 利用率、Token 收入、毛利、SLA 和异常 |
| 模型运营 | 配置模型、推理端点、售价、容量、上下架和路由 |
| 资源运维 | 处理 GPU、实例、模型部署、端点健康和容量告警 |
| 财务/管理员 | 调整额度、查看 Token 用量、资金流水与审计 |
| API 用户 | 创建 Key、调用模型、查看用量、额度和错误 |
| 实例用户 | 购买 GPU 实例、连接环境、开关机和释放 |

### 2.3 暂不服务的对象

- 需要开放供应商入驻、竞价和平台分账的双边市场；
- 需要数千卡训练集群、复杂拓扑和调度优化的大型 AI 基础设施客户；
- 只购买 Serverless 推理 API、不需要 GPU 实例的客户；
- 期望系统自动解决机房网络、驱动、散热和硬件故障的个人 Host。

## 3. 产品原则

### 3.1 单资源方、单部署优先

首期每套部署服务一个资源运营主体，控制面、数据库、推理网关和节点 Agent 完全运行在客户环境。品牌、域名、客户、价格和数据相互独立。不建设厂商托管的共享 SaaS 多租户隔离、平台计费和租户管理后台。

### 3.2 固定资源来源，不做开放市场

资源只来自运营方自有节点或少量固定合作方。合作方通过内部 Provider Adapter 接入，不拥有供应商账号、供应商工作台或公开上架权限。

### 3.3 Token 是推理业务的真实计量单位

推理 API 必须分别记录输入与输出 Token，以推理运行时返回的用量为事实来源，并保留平台核验数据。首期使用管理员授信或线下收款，不提供在线支付；但 API Key 额度、Token 扣费、幂等和失败不扣费必须真实生效。

### 3.4 一套资源池，两种收益模式

同一份 GPU 容量可以被分配为实例出租或模型推理服务，但同一容量不能重复出售。资源从空闲、预留、实例占用、推理部署占用到释放必须可追踪、可重试、可对账。

### 3.5 Adapter 负责执行，控制面负责业务

Resource Adapter 处理 GPU/资源系统差异；Inference Runtime Adapter 处理 vLLM、NIM 等运行时差异；订单、价格、权限、资金、Token 用量、任务状态和审计由控制面统一管理。

### 3.6 人工兜底必须受控

允许运营人员重试、取消、重新同步或发起对账，但不允许绕过状态机直接修改实例、订单、余额或库存结果。所有高风险操作必须记录原因、操作人和前后状态。

## 4. 产品边界

### 4.1 主路径

    资源接入
    → 库存同步
    → 分配为 GPU 实例或推理部署
    → 部署/接入模型端点
    → 健康检查与容量确认
    → 设置 Token 售价并发布模型
    → 用户创建 API Key
    → 鉴权、限流与路由
    → 推理调用与 Token 计量
    → 余额扣减、用量与毛利
    → 停止部署并释放资源

### 4.2 产品应保留的能力

- 资源来源、区域、SKU、成本、售价和库存；
- 模型目录、推理副本、OpenAI 兼容 API 和网页 Chat；
- API Key、Key 额度、Token 用量、输入/输出价格和扣费；
- 用户账号、会话、安全校验和基础资料；
- 订单、额度、资金流水和失败补偿；
- 实例创建、开机、关机、释放和连接信息；
- 幂等、Outbox、重试、超时恢复和状态对账；
- 用户控制台与瘦运营后台；
- 成本字段隔离、后台权限、审计和生产安全开关；
- OpenAPI 契约、数据库迁移、部署配置和健康检查。

### 4.3 产品应增加的能力

| 能力 | 原因 | 优先级 |
|---|---|---:|
| OpenAI-compatible 推理后端 | 将现有 Mock 网关接到真实 vLLM 端点 | P1 |
| 模型与推理副本创建/配置 | 让运营方在后台发布自己的模型服务 | P1 |
| API Key 的 RPM/TPM/并发限流 | 防止滥用并形成可销售套餐 | P1 |
| 端点健康、延迟、吞吐与错误监控 | 决定模型 API 是否可运营 | P1 |
| Token 计量对账与失败不扣费 | 决定收费可信度 | P1 |
| GPU 容量分配模式 | 防止实例和推理重复出售同一资源 | P1 |
| Docker 节点 Agent 与 vLLM 部署编排 | 从“接入端点”升级为“自动部署模型” | P1 |
| 库存同步与平台/上游对账 | 避免超卖、漏回收和状态漂移 | P1 |
| 镜像/启动模板与 Provider 参数映射 | 没有可用环境就没有真实开发体验 | P1 |
| SSH 公钥与连接凭据安全管理 | 真实交付不能继续使用演示提示 | P1 |
| 品牌、域名、客服、协议和基础主题配置 | 白牌产品必须由资源方自主配置 | P1 |
| 线下收款后的人工授信/充值 | 首期绕开在线支付但保留可审计交易 | P1 |
| 异常处置台与差异对账 | 让运营能够处理真实 Provider 故障 | P1 |
| 安装检查、升级与备份恢复工具 | 私有化交付必须可安装、可维护 | P2 |
| 团队、项目、配额和成本中心 | 支持企业/高校内部 GPU 共享 | P3 |
| 多 Provider 与路由策略 | 单 Provider 验证后再扩展 | P3 |
| 可信计量、在线支付与账单 | 仅在上游数据与财务规则成熟后增加 | P3 |
| API/SDK、Webhook 与自动化 | 服务成熟客户和集成场景 | P2 |

### 4.4 产品应减少或移除的能力

| 能力 | 决策 | 原因 |
|---|---|---|
| 拼租卡 | 移出路线图 | 依赖组团、预付款、退款和人工销售，不强化主定位 |
| 裸金属询价与线索池 | 移出产品 | 属于 CRM/项目销售流程，可由外部工具承载 |
| 解决方案获客页和内容后台 | 降为自定义静态内容 | 不建设 CMS 和营销中台 |
| 开放供应商入驻 | 明确不做 | 会引入认证、分账、SLA 和争议处理平台责任 |
| 自研 Kubernetes/GPU 调度器 | 明确不做 | 应接现有系统，不与底层基础设施竞争 |
| 九角色复杂后台 | 缩为管理员、运营、只读审计三类 | 早期客户团队小，复杂 RBAC 成本高 |
| 优惠券、邀请、活动、发票 | 后置 | 增长与财务复杂度高，首批客户可线下解决 |
| 微信登录、短信登录、实名 | 后置并按部署选择 | 依赖地区、供应商和合规方案 |
| 精确按秒计费与自动退款 | 后置 | 必须先有可信用量与财务对账 |
| 社区镜像市场 | 不规划 | 带来审核、安全与许可证责任 |
| 完整多租户 SaaS | 不规划首期 | 与单资源方私有部署目标冲突 |

## 5. 产品形态与信息架构

### 5.1 产品形态

每次私有化部署包含五个部分：

1. 用户门户：品牌首页、资源目录、登录和帮助；
2. API 用户控制台：模型、API Key、用量、额度和调用文档；
3. GPU 实例控制台：实例、订单、连接与生命周期；
4. 运营控制台：资源、模型、端点、商品、用户、交易和审计；
5. Adapter 层：连接 GPU 资源系统和 vLLM/NIM 等推理运行时。

### 5.2 用户门户

    /
    ├── 产品首页
    ├── 模型 API /models
    ├── GPU 资源 /market
    ├── 登录 /login
    ├── 注册或邀请激活 /register
    ├── 帮助 /help
    └── 协议 /legal/*

首期首页只负责解释当前资源方提供什么、如何购买和如何获得支持，不建设解决方案矩阵、行业案例库、活动中心和内容 CMS。

### 5.3 用户控制台

    /console
    ├── 概览
    ├── API Keys
    ├── Token 用量
    ├── 创建实例
    ├── 实例
    ├── 订单与额度流水
    ├── SSH 公钥/安全
    └── 个人资料

模型目录、API Key 和 Token 用量属于默认信息架构；网页 Chat 是模型 API 的体验入口。GPU 实例入口可以按部署方的经营模式关闭，但资源与推理运营能力不能关闭。

### 5.4 运营控制台

    /admin
    ├── 交付看板
    ├── 资源来源与 Provider
    ├── 模型、推理端点与路由
    ├── API Key、Token 用量与限流
    ├── SKU、套餐与库存
    ├── 实例与任务
    ├── 用户与额度
    ├── 订单与资金流水
    ├── 异常与对账
    ├── 品牌与系统配置
    └── 审计日志

后台不建设 CRM、工单、营销、内容、发票、开放供应商和底层节点调度中心。需要这些能力时优先集成专用系统。

## 6. 核心功能需求

### 6.1 统一资源池与分配模式

每份 GPU 容量必须处于以下一种模式：空闲、实例预留、实例占用、推理部署预留、推理部署占用、维护。实例订单和推理部署使用同一份资源事实，不能各自维护互不相干的库存。

首期允许运营人员将独立资源来源或 SKU 固定分配给实例或推理服务；自动弹性路由后置。所有模式切换必须确认活动实例、推理请求、模型缓存和数据清理状态，并写入审计。

### 6.2 部署与品牌配置

目标：资源方可以在不修改源码的情况下，把系统配置成自己的服务。

必需配置：

- 品牌名、Logo、主题色和浏览器图标；
- 公开域名、后台域名、客服入口和联系信息；
- 默认语言、币种、时区和价格展示规则；
- 服务协议、隐私政策、使用限制和反滥用规则；
- 注册方式固定为开放注册，不使用邀请码或管理员邀请；
- 功能开关：在线支付、短信、推理模块等默认关闭。

验收：更换品牌配置不需要重新构建前端；生产缺少关键域名、密钥或协议时给出明确阻断或告警。

### 6.3 资源与运行时接入

目标：在不修改订单与实例业务层的情况下接入一个真实资源系统。

Resource Adapter 最小能力：

- 健康检查；
- 获取或同步可售库存；
- 创建实例；
- 查询实例状态；
- 开机、关机和释放；
- 获取连接信息；
- 支持客户端请求号或平台幂等映射；
- 返回稳定错误类型、外部请求 ID 和可重试标记。

Inference Runtime Adapter 最小能力：

- 检查端点健康、模型标识和 OpenAI 兼容能力；
- 转发 Chat Completions 的流式与非流式请求；
- 返回运行时提供的输入、输出 Token 和结束原因；
- 将超时、容量不足、限流、模型错误和运行时故障映射为稳定错误；
- 不向 API 用户暴露上游地址、凭据和内部响应头。

接入工具：

- Provider 能力清单与契约测试；
- 沙箱/测试资源配置；
- 凭据加密存储与轮换；
- 超时、重试、限流和熔断配置；
- 原始外部错误仅进入受限日志，用户端使用平台稳定错误码；
- 测试创建、状态查询、开关机、释放和重复请求的诊断命令。

非目标：首期不要求 Provider 实现节点调度、迁移、扩缩容、MIG、共享存储和复杂网络。

### 6.4 资源、SKU 与库存

资源模型至少包含：资源来源、区域、GPU 型号、显存、卡数、CPU、内存、系统盘、可售库存、Provider SKU 映射和状态。

要求：

- 成本与销售价分离，用户 API 永不返回供应成本；
- 库存支持人工维护或 Provider 同步，但必须标记数据来源与更新时间；
- 下单事务内再次校验并预占平台库存；
- 定期对账平台可售量、活动实例和 Provider 实际状态；
- 差异进入异常队列，不自动覆盖订单与资金结果；
- SKU 下架后不影响用户查看和释放已有实例。

### 6.5 模型、部署模板与推理副本

目标：运营方可以把一个经过验证的模型运行时发布为稳定模型 API，并为 GPU 实例保留开发环境模板。

模型字段：

- 对外模型 slug、名称、上下文长度和能力标签；
- 推理后端类型、内部端点、上游模型名和凭据引用；
- 副本权重、健康、容量 TPM、超时和启停状态；
- 输入/输出 Token 成本价、销售价和发布状态；
- 兼容的 GPU、运行时、模型版本与许可证记录。

P1 同时支持登记已有 OpenAI-compatible 端点，以及通过客户节点 Agent 自动拉取模型、启动单机 Docker vLLM、缓存权重和管理部署生命周期。Kubernetes、NIM Operator 和多节点推理后置。首期只允许运营维护经过验证的模型模板，不建设开放模型市场。

### 6.6 API Key、限流与安全

首批试点使用手机号或邮箱直接注册 + 密码登录，不设置邀请码门槛。

要求：

- 注册和登录在手机号、邮箱中二选一；用户注册后可同时绑定两种方式，且每个手机号和邮箱只能属于一个用户；
- 解绑不得改变用户 ID 或业务数据归属，并且必须至少保留一种可登录方式；
- HttpOnly Cookie 会话、CSRF/Origin、频控和密码安全继续保留；
- 用户可维护 SSH 公钥；
- API Key 只在创建时显示一次，服务端只存不可逆哈希；
- 每个 Key 可配置额度、RPM、TPM、并发和允许模型；
- 吊销、用户封禁和额度耗尽必须在下一次请求前生效；
- 连接密码、令牌等敏感凭据不得写入普通日志或长期明文展示；
- 管理员只能执行重置/轮换，不能查看不可逆的用户秘密；
- 封禁用户后禁止新建和高风险操作，但已有资源如何处置必须由规则明确决定；
- 所有管理员授权、额度调整和用户状态变更写审计。

当前本地闭环使用密码完成绑定二次确认。短信和邮件验证码、目标地址所有权验证属于生产外部接入验收，不把未验证的本地绑定表述为生产级换绑。

### 6.7 Token 计量、额度与订单

首期交易模型：线下收款或合同确认后，管理员向用户账户增加可用额度；GPU 实例按套餐扣费，模型 API 按实际输入/输出 Token 扣费。

要求：

- 额度调整必须填写外部凭证号、原因和备注；
- 增加、扣减、退款均形成不可变资金流水；
- 订单、库存预占、实例任务和 Outbox 在同一事务；
- 同一用户重复提交同一请求不得重复扣款或占库存；
- 创建失败按明确规则退回额度和库存；
- 管理员不能直接编辑历史流水；冲正使用新流水记录；
- 首期不提供真实在线支付、自动提现、原路退款或税务发票。

推理计量额外要求：

- 以运行时返回的 Token 用量为优先事实来源；
- 请求进入前校验余额和 Key 额度，完成后按实际用量结算；
- 上游未返回有效推理结果、连接失败或平台取消时不得按成功请求收费；
- 同一请求 ID 重放不得重复计费；
- 流式请求只结算一次，并记录客户端中断和上游结束状态；
- 价格版本必须随用量事件固化，历史账单不随调价变化。

### 6.8 模型 API 调用

用户流程：

1. 浏览已发布模型和输入/输出价格；
2. 登录并创建带额度与限流策略的 API Key；
3. 使用 OpenAI SDK 指向平台 base URL；
4. 网关鉴权并选择健康推理副本；
5. 返回流式或非流式响应；
6. 记录 Token、延迟、副本、价格版本、成本和扣费；
7. 用户和运营方分别查看用量与经营指标。

P1 首期支持 Models 与 Chat Completions；Embeddings、Responses、图像、语音和视频接口按真实客户需求后置。

### 6.9 实例交付

用户流程：

1. 选择 SKU、套餐和启动模板；
2. 添加或选择 SSH 公钥；
3. 确认价格、时长、到期与数据删除规则；
4. 提交后立即获得实例 ID 和任务 ID；
5. 页面轮询任务并展示排队、创建、运行或失败；
6. 运行后展示 SSH/Jupyter 等实际连接方式；
7. 用户可执行开机、关机和释放；
8. 释放前二次确认数据删除后果；
9. 释放成功后归还库存并保留订单、任务和审计记录。

要求：

- HTTP 成功不等于交付成功；
- 平台状态与 Provider 状态分离映射；
- 每个长任务可重试且重复消费安全；
- 超时任务可被扫描和恢复；
- 失败原因区分用户可处理、运营可重试和需联系 Provider 三类；
- 连接信息必须来自真实 Provider，Mock 地址不得在生产出现。

### 6.10 异常处置与对账

运营人员需要看到：

- 卡住、失败、超时和重试中的任务；
- 平台与 Provider 状态不一致的实例；
- 已扣额度但未交付、已释放但未归还库存等业务差异；
- Provider 健康、最近同步时间和连续失败次数；
- 推理端点健康、首 Token 延迟、吞吐、错误率和容量；
- Token 用量、平台扣费与上游运行时用量差异；
- 每次重试、取消、补偿和人工确认的审计记录。

允许操作：重新查询、重试原任务、发起补偿、隔离 SKU、暂停新订单、记录外部工单号。

禁止操作：直接把实例改成运行、直接把订单改成成功、覆盖历史流水、无审计地增加库存。

### 6.11 可安装与可维护

私有化产品必须提供：

- 开发、试点和生产三套配置说明；
- 安装前依赖与端口检查；
- 数据库安全升级脚本；
- Provider 与关键依赖健康检查；
- 结构化日志、基础指标和告警出口；
- 数据库备份与恢复演练文档；
- 版本号、迁移说明和升级回滚前检查；
- 配置与密钥分离，禁止将真实密钥提交到仓库。

## 7. 版本路线图

### 7.1 P0：双业务 Mock 技术闭环（当前基本完成）

目标：证明控制面状态机与工程骨架成立。

- SKU、价格、库存、模型目录与市场筛选；
- 用户、演示额度、订单和资金流水；
- MockProvider 创建、开关机、释放和连接信息；
- Mock 推理、API Key、Token 用量、价格和余额扣减；
- Outbox、幂等、重试、库存/额度补偿；
- 用户控制台、瘦后台、审计和安全基线。

退出条件：本地 Mock 闭环和自动化测试通过，但不得宣传为真实 GPU 交付。

### 7.2 P1：首个真实 Token 商业化试点（下一阶段）

目标：在一个真实环境中，把一个真实 GPU 推理端点发布成可鉴权、可计量、可收费的模型 API，并继续验证 GPU 实例交付。

- 接入一个真实 vLLM/OpenAI-compatible 推理端点；
- 部署客户节点 Agent，并通过受控参数启动、停止和检查 Docker vLLM 容器；
- 节点 Agent 不接受任意命令、任意挂载或任意容器参数；
- 后台可创建模型、配置副本端点、成本、售价、容量和上下架；
- API Key 的 RPM/TPM/额度限制真实生效；
- 流式与非流式推理均记录真实 Token，并保证幂等与失败不扣费；
- 记录端点健康、延迟、错误率、Token 收入、成本与毛利；
- 接入一个真实 Resource Provider，保留 GPU 实例创建与释放闭环；
- 增加库存/容量同步、差异对账和异常处置；
- 增加品牌、域名、客服和协议配置；
- 将演示余额升级为可审计的人工授信/线下充值；
- 完成生产配置、备份恢复、HTTPS、独立后台域名和真实 MFA 验收。

退出条件：

1. 一个真实资源方完成独立部署；
2. 至少一个真实模型通过平台 API 提供服务；
3. 至少 3 个 API Key 完成累计 1,000 次真实请求；
4. API Key 吊销、额度、RPM/TPM 和模型权限真实生效；
5. 流式、非流式、失败、超时和重复请求的计量结果可解释且不重复扣费；
6. 平台 Token 用量与推理运行时无未解释差异；
7. 模型端点连续运行 72 小时，严重故障可告警并停止路由；
8. 至少一个真实 GPU SKU 完成实例创建、连接和释放；
9. 备份恢复、HTTPS、后台域名和真实 MFA 验收通过。

### 7.3 P2：可复制销售的私有化产品

目标：第二个客户不再依赖大量定制开发。

- 标准安装包、安装诊断、升级与配置迁移；
- Resource/Inference Adapter 开发模板、契约测试和接入文档；
- 标准化节点 Agent 安装、升级、日志和故障诊断；
- 推理部署滚动升级、资源迁移和更完整的模型缓存策略；
- 品牌配置后台与可复用页面内容；
- 套餐到期、续期、提醒和受控的人工退款/冲正；
- Webhook、基础开放 API 和外部身份集成；
- 可配置的管理员、运营、只读审计角色；
- 产品许可证、版本支持和服务状态信息。

退出条件：第二个资源方在不修改核心业务代码的前提下完成部署和 Provider 接入。

### 7.4 P3：规模化与企业扩展

以下能力必须由真实客户需求和付费意愿触发，不按“云平台标配”自动开发：

- 多资源来源、跨部署路由和故障切换；
- 在线支付、退款与正式财务对账；
- 团队、项目、配额、成本中心和企业 SSO；
- 自定义镜像、持久化存储和端口管理；
- 高可用部署、跨区域和大规模任务处理；
- Kubernetes/KServe/NIM Operator、Serverless 自动扩缩容和多节点推理。

明确不进入路线图：开放供应商市场、自动拼租、完整 CRM、自研底层 GPU 调度器和社区镜像市场。

## 8. 核心指标

### 8.1 北极星指标

每个活跃资源方每月通过平台完成并成功计费的真实模型 API Token 数及毛利。

“成功计费”必须同时满足：API Key 有效、推理端点返回有效结果、Token 用量可核对、只扣费一次、价格版本可追溯。GPU 实例交付数作为第二核心指标。

### 8.2 P1 试点指标

| 指标 | 目标 |
|---|---:|
| 从完成 Provider 配置到首个真实实例运行 | ≤ 1 个工作日 |
| 从配置推理端点到首个真实 API 调用 | ≤ 1 小时 |
| 真实推理请求成功率 | ≥ 99%（不含用户请求错误） |
| Token 重复扣费或失败误扣费 | 0 |
| Key 吊销与额度策略失效 | 0 |
| 真实实例交付成功率 | ≥ 95% |
| 重复请求导致的重复扣款/重复实例 | 0 |
| 释放后库存未归还且未告警 | 0 |
| 平台与 Provider 未解释状态差异 | 0 |
| 用户从下单到首次连接成功率 | ≥ 90% |
| 严重任务异常可定位率 | 100% |

### 8.3 经营指标

- 可售 GPU 数与售出率；
- 不同 SKU 的订单数、交付数和失败率；
- 资源方设置的销售收入、供应成本和估算毛利；
- 活跃用户、复购用户和平均使用时长；
- 运营人工介入次数与平均处理时长；
- Provider 可用率、同步延迟和任务耗时分布。
- 输入/输出 Token、请求数、首 Token 延迟、吞吐和错误率；
- 每个模型/副本的成本、收入、毛利和 GPU 利用率。

P1 的金额仅用于资源方内部经营参考，不宣称为经审计的精确计费结果。

## 9. 商业化设计

### 9.1 推荐收费结构

首期采用项目制进入、产品化续费：

1. 私有化部署费：环境配置、品牌初始化和上线支持；
2. Provider 接入费：按一个资源系统的接口范围报价；
3. 年度维护费：安全更新、版本升级、缺陷修复和基础支持；
4. 企业扩展费：SSO、团队、计费、存储或专属集成单独报价。

首期不建议按交易抽成。目标客户选择私有化系统的重要原因之一，就是保留自己的客户与经营关系；按 GPU 数或部署实例授权比抽佣更容易解释。

### 9.2 产品版本建议

| 版本 | 适用对象 | 核心能力 |
|---|---|---|
| Community/Demo | 技术评估 | MockProvider、本地闭环、开发文档 |
| Operator | 中小资源运营方 | GPU 纳管、模型 API、Key、Token 计费、实例交付 |
| Enterprise | 企业/高校或规模客户 | SSO、团队配额、审计扩展、高可用和专属支持 |

版本划分是商业建议，不代表当前已具备许可证系统、自动升级或 Enterprise 能力。

## 10. 风险与依赖

### 10.1 最大风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 找不到愿意试点的真实资源方 | 产品停留在演示系统 | 暂停横向开发，优先访谈和签试点 |
| 上游 API 缺少幂等、状态查询或释放接口 | 无法保证可靠交付 | 接入前做能力清单；不足时明确人工交付边界 |
| 库存和用量数据不可信 | 超卖、计费争议 | 先固定套餐与人工授信，建立对账再做按量 |
| 连接和网络条件不可控 | HTTP 成功但用户不可用 | 将真实 SSH/Jupyter 连接纳入验收 |
| 私有部署环境差异大 | 每个客户变成定制项目 | P2 前完成安装诊断和支持矩阵 |
| 功能继续向大而全云平台膨胀 | 延迟真实验证 | 新功能必须证明能提升接入、交付或复制销售 |

### 10.2 外部前提

进入 P1 前，试点方必须提供：

- 可测试的 GPU 资源与稳定测试环境；
- 完整 Provider API 文档、测试凭据和限流说明；
- 库存、创建、查询、开关机、释放、连接信息接口；
- GPU 型号、区域、套餐、成本、销售价和售后规则；
- 品牌、域名、客服、协议和部署环境；
- 指定运营与技术负责人参与异常确认和验收。

如果对方没有可调用的资源 API，试点只能定义为“控制面 + 人工交付台”，不能承诺自动 GPU 交付，也不应临时自研底层调度系统。

## 11. 产品决策门槛

任何新需求进入 P1/P2 前，至少回答以下问题：

1. 它服务资源运营方还是最终用户？
2. 它是否直接提高真实 Provider 接入、交付成功率或部署复制效率？
3. 首个试点客户是否明确需要并愿意共同验收？
4. 是否可以交给现有 CRM、支付、监控、身份或调度系统完成？
5. 是否引入资金、计量、隐私、供应商或平台责任？
6. 如果暂不实现，真实交付闭环是否仍然成立？

优先级判断：

- 直接决定真实 GPU 能否交付：P0/P1；
- 决定第二个客户能否低成本复制：P2；
- 只提升功能完整度或对标程度：默认后置；
- 改变产品为开放市场、底层调度器或完整零售云：拒绝或另立产品。

## 12. 待产品负责人确认

以下问题不会阻塞 PRD 成为当前基线，但会决定 P1 试点方案：

1. 是否已有可接入的真实 GPU、模型和测试环境？
2. 首个对外模型及其商业使用许可证是什么？
3. API Key 首期是否还需要并发限制和更细的模型白名单策略？
4. Token 价格使用人民币还是美元？是否分别设置缓存输入价格？
5. 首个试点采用管理员授信，还是接入现有支付/余额系统？
6. 产品采用开源核心 + 商业服务，还是闭源商业授权？

在以上问题确认前，可以继续完善 OpenAI-compatible backend、模型/副本运营、API Key、Token 计量、凭据安全、对账和异常处置；不应提前开发在线支付、多节点调度、开放市场或完整多租户 SaaS。
